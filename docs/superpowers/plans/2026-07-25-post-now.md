# "Post now" in the Composer — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let the composer publish a post immediately instead of scheduling it for a date and time — and be honest about what "immediately" actually means in this system.

## Design (settled with the owner)

- **Post now bypasses the approval gate.** Both existing channels have `requires_approval = 1`, which would otherwise land the send in `pending_approval` and publish nothing. The owner's decision: approval exists to gate queued and auto-filled content nobody individually reviewed; someone who just composed a post and clicked publish *is* the approver. So a Post-now send is created as `scheduled`, never `pending_approval`.
- **It is not instant, and the UI must not imply it is.** The worker polls every `WORKER_POLL_INTERVAL` (30s by default) and only picks up `status='scheduled' AND scheduled_at <= now AND is_held = 0`. Post now sets `scheduled_at` to the current instant; publishing happens on the next poll.
- **Two conditions silently prevent it working, and both must be surfaced *before* the click:**
  - `DRY_RUN=1` (currently the case) — the worker will simulate and post nothing.
  - The worker isn't running — nothing will pick the send up at all.
  Neither should *block* the action (a queued send is still valid and will go out when the worker returns), but the button must say plainly what will happen.

## Global Constraints

- **Never modify `data/socialscheduler.db`.** Two live channels (Instagram, Threads) publish for real. WAL mode — any copy needs the `-wal`/`-shm` sidecars.
- **Never flip `DRY_RUN` as part of this work.** It stays at `1`.
- Worker tests: `.venv/bin/python -m pytest worker/tests -q` (**324 passing**, ~110s; let it finish). Dashboard: `cd dashboard && npx tsc --noEmit`.
- No new dependencies. No schema changes — this needs none.
- Nothing about scheduled posting changes; a post with a date and time behaves exactly as today.
- Commit after each task.

### Task 1: Server-side support for an immediate publish

**Files:** Modify `dashboard/app/api/posts/route.ts`, `dashboard/lib/queries.ts` (if the status/scheduled_at decision lives there); create/modify a small server helper for publish-readiness; add `dashboard/scripts/smoke-post-now.mjs` following the existing smoke-script pattern

**Interfaces produced (Task 2 consumes these):**
- `POST /api/posts` accepts `post_now: true`.
- A server-side helper reporting publish readiness — at minimum `{ dryRun: boolean, workerOnline: boolean }` — for the composer page to render. `dashboard/lib/config.ts` already reads the repo-root `.env` (use it for `DRY_RUN`; treat any value other than `0`/`false` as on, matching how the worker reads it), and `getWorkerStatus()` in `dashboard/lib/queries.ts` already reports worker liveness from the heartbeat.

- [ ] **Step 1: Write the smoke test first**

There is no JS unit runner in this project; the established pattern is a Node smoke script driving the real routes against a **scratch database copy** — read `dashboard/scripts/smoke-caption-limit-routes.mjs` and follow it closely, including how it stands up an isolated server and cleans up.

Cover:
1. `post_now: true` with no date/time → **201**, and the created publication has `status = 'scheduled'` (**not** `pending_approval`) even for a channel with `requires_approval = 1`, with `scheduled_at` at or before "now".
2. The same request for a channel **without** approval → also `scheduled`.
3. A normal scheduled request (date + time, no `post_now`) → unchanged behaviour, including still landing `pending_approval` for an approval-required channel. **This is the regression guard — make it explicit.**
4. `post_now: true` **and** a date/time supplied → decide one behaviour and pin it: either reject with a 400 or document that `post_now` wins. Don't leave it ambiguous.
5. All existing validation still applies to a Post-now request — no channels selected, an unsupported post type for a target, an over-limit caption, a text post with no caption. Post now must not become a hole around the checks the other paths enforce.

Keep the scheduled path byte-identical. Put a comment at the status decision recording *why* approval is bypassed here, so the next reader doesn't "fix" it.

- [ ] **Step 4: Add the publish-readiness helper** described above, server-side only. Never expose anything from `.env` beyond these two booleans — no paths, no tokens.

### Task 2: The Post now control in the composer

**Files:** Modify `dashboard/components/composer.tsx`, `dashboard/app/compose/page.tsx`

**Read `dashboard/components/composer.tsx` in full before changing anything** and follow its existing state, styling and submission conventions. It is the most complex component in the app and has been reworked several times; each pass was verified as behaviour-preserving for the existing flow.

- [ ] **Step 1: Add the choice.** In the Schedule section, let the user choose between **Schedule** (today's date/time picker, the default) and **Post now**. When Post now is active, hide the date/time inputs and submit `post_now: true` instead of a date/time. Turning it off restores the picker with whatever was typed.

- [ ] **Step 2: Be honest about what will happen.** Next to the Post-now control, render the state from Task 1's helper (pass it in from the server component `dashboard/app/compose/page.tsx`, which can call it directly):
  - Normal: say it will publish on the next worker check, within about a minute — not "instantly".
  - `DRY_RUN=1`: say plainly that dry-run is on, so this will be **simulated and nothing will actually post**, and name the `.env` setting to change.
  - Worker offline: say nothing will pick it up until the worker is running, and that the send will simply wait.
  Neither condition disables the button — a queued send is still valid — but neither may be silent.
  Also note that Post now skips the approval step for channels that require it, so that isn't a surprise.

  - Toggling back restores the picker and any typed date/time.
  - Composing with Post now creates a publication that is `scheduled` (not `pending_approval`) and due immediately.
  - **Clean up anything you create** — delete the test post and its publications, and report the row counts before and after. **Do not modify `data/socialscheduler.db` by hand beyond removing what you created**, and do not let a real post go out: `DRY_RUN` stays `1` throughout, so a worker cycle would only simulate.

- Post now creates an immediately-due `scheduled` publication, bypassing approval, with every other validation still enforced.
- The scheduled path is unchanged, including still honouring `requires_approval` — pinned by a test.
- Dry-run and worker-offline are visible in the composer before the click, not discovered afterwards.
- `tsc` clean; the worker suite still green; the real database left exactly as found.
